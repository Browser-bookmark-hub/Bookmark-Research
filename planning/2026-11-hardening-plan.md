# Bookmark Research 加固计划

> 2026-11-03 · 实测对象：`书签画布`（46 节点 / 13 连线 / 36 栏目 JSON）
> 运行版本：`0.6.0+source.fabc11bba8230028`，与仓库 `src/` 逐字节一致
> 实测痕迹（临时源、临时包副本）已清理

## 一句话判断

索引层已经成熟：文件级 sha256 增量、内容寻址的版本号、事务回滚、live 源自动收录都经得起实测。Wiki 层结构严谨但几乎没被用过，缺的只是热度与可观测性。搜索层实现了宪章的大部分，硬缺口集中在浏览器渲染抓取、宿主搜索回流，以及 agentic 搜索的循环与改写。

| 关键数字 | 实测 |
| --- | --- |
| 全量导入 | 0.58 s，37 文件、5006 项 |
| 无改动重扫 | 0.014 s，changed 0 / skipped 37，版本号不变 |
| 单文件改动 | 0.018 s，只重解析该文件 |
| 监控轮询 | 间隔 1 s，实测改动数秒内自动收录，无需显式 sync |

## 新增能力的接入点

现有管线自上而下是：导入与监控 → 索引 → 检索入口 → 抓取与研究 → 存档与知识。计划新增的能力各自接到其中一段，接入点决定顺序。

| 计划新增 | 接入点 | 为什么在这里 |
| --- | --- | --- |
| 轮询预筛 mtime + size | 导入与监控 | 大包每秒重哈希全部文件的成本先降下来 |
| 多跳关系查询 + URL 反向索引 | 索引 | 沿连线与组包含走 N 跳，并回答“这个链接出现在哪” |
| 加权排序层 + 中文分词治理 | 检索入口 | 字面命中仍是硬过滤，分值只作提示；去掉跨词 bigram 噪声 |
| 浏览器渲染 · 宿主回流 · agentic 循环 | 抓取与研究 | 脚本页可取正文；宿主结果可合并；模型可迭代搜索 |
| 读取计数 · 书签引用 · 存档 URL 去重 | 存档与知识 | 让“Wiki 用了多少次”可测，并让页面能反查到具体书签 |

排序层与分词治理只动检索入口，风险最低；浏览器渲染与宿主回流动的是网络与预算路径，风险最高，放在后面。

## 目标与非目标

**目标**：索引层在千级到万级条目下保持“改动秒级可见、全量导入亚秒”；检索在保持字面命中契约的前提下给出可解释的分值与关系；搜索层补齐宪章里的抓取与迭代能力；Wiki 从“结构完整但闲置”变成日常可复用的知识层，并且用量可测。

**非目标**：不做语义检索与 embedding；不让插件反向调用宿主工具；不让插件写画布包；不在本轮改动 TUI 与安装流程。这些都留给后续判断。

规模记号：**S** 约 1 天内，**M** 约 2 到 4 天，**L** 约 1 到 2 周。

## P0 数据现状与可观测性

先把被冻结的源和无法测量的行为修掉，后面所有改动才有可信的对照。

### P0-1 把主源刷新到最新提交 · S

- **现状**：主源是 snapshot 模式，`last_sync` 停在 2026-11-01，5001 项且全部 `revision=1`；snapshot 源永远不会被监控自动刷新。
- **改动**：用同一个 `source_id` 重新 `sync_package`（`completeness:"complete"`），观察返回的 diff 计数；若要长期跟随包变化，改用 `mode:"live"`。若该源已被某个研究清单冻结引用，先确认再动。
- **验收**：items 从 5001 变为 5006；变更只落在 A-3-2、A-3-4、A-4 等实际改动文件；`retained_missing_files` 为空；被改动文件的条目 `revision > 1`，未改动文件保持 1。

### P0-2 清掉同路径的旧源 · S

- **现状**：同一目录注册了三个源，旧源带着包里已不存在的文件（`retained_missing_files` 非空），检索时容易读到过期投影。
- **改动**：`python3 src/cli.py source merge <重复源> <保留源>`，内容版本不一致时退回 `source remove --confirm`；先跑不带 `--confirm` 的干跑看计数。
- **验收**：一个路径只剩一个源，全部源的 `retained_missing_files` 为空，`index_status` 输出可直接作为基线留档。

### P0-3 让 Wiki 的用量可测 · M

- **现状**：磁盘上没有读日志：`log.md` 只记写入，`wiki_search` 与 `wiki_get` 完全不落痕。“日常问答调用频率”目前无法回答，只能用写入频率（约每月 1 到 2 页）近似。
- **改动**：在 Wiki 目录下加一份追加式计数（时间、工具名、page_id、命中数、是否复用），只记标识与计数，不记查询文本与正文；写入路径复用现有 log 时机，读取路径挂在 `wiki_search`、`wiki_get`、`plan_research` 的 wiki 分支上。
- **验收**：能直接回答“过去 30 天命中几次、写入几次、命中后复用了哪些页”；计数文件损坏或缺失时检索行为完全不变；有对应单测。

### P0-4 修掉文档与实现的一处出入 · S

- **现状**：`references/package-semantics.md` 写“公共查询不使用 BM25”，但存档层的 FTS 排序确实按 `bm25(page_text)` 排（`src/raw_library.py:380`）。这句话对 items 检索成立，对存档不成立。
- **改动**：在文档里分开表述：书签 items 检索是字面命中、无 BM25；存档正文检索用 BM25 排序；并在同一处点明 Wiki 检索的排序公式。
- **验收**：三处排序口径在一篇文档里能一次读懂，且与代码逐条对得上。

## P1 索引层：打分与关系图

保持“字面命中是硬过滤”的契约不变，只在其上补分值、关系与开销。

### P1-1 可选加权排序层 · L

- **现状**：书签检索是纯字面子串匹配（3 字符以上走 FTS5 trigram，短词回退 LIKE），没有任何字段权重；唯一的加权在 `plan_research`：`len(term)/命中卡片数 × 密度`。画布文档里的 140 / 135 / 110 / 90 分矩阵与全屏加成在这里没有对应实现。
- **改动**：在返回结果里增加 `field_hits` 与 `score`：标题前缀、标题包含、tag、note、folder_path、URL 分档权重，叠加上时间加权（`added_at` 按 high / medium / low 分档）。命中集合与分页语义完全不变，分值只作提示，并在输出里显式标注为 hint。默认关闭或按需启用，避免改变现有宿主提示的契约。
- **验收**：同一查询的命中条数与顺序在开关关闭时逐条不变；开启后字段权重与同分决胜有单测覆盖；`plan_research` 的卡片排序可选用同一套分值而不改变其既有输出字段。

### P1-2 中文分词噪声治理 · M

- **现状**：`plan_terms` 对超过 4 字的中文串输出全部相邻 bigram，实测一个中文问题会产生 `地部`、`署有`、`些路` 这类跨词碎片，它们参与权重分母与 `term_cards` 统计。
- **改动**：只保留与整串边界一致的 bigram，或对无法在包内命中的碎片降权；4 字以内仍整词优先。保留“一个词只指向一棵树就是命名”这一判据。
- **验收**：固定问题的 `terms` 不再含跨词碎片；用 15 个已知目标做回归，召回不下降；`term_cards` 判据的既有测试全绿。

### P1-3 多跳关系查询 · M

- **现状**：`get_context` 只给 1 跳：`edges` 与 `related_nodes` 止于直接端点；递归查询目前只用在文件夹子树（`src/bookmark_index.py:882`）。问“改这张卡会影响谁”没有工具能答。
- **改动**：新增遍历入口：从节点、栏目或条目出发，沿 `edges` 与 `memberships` 走 N 跳，返回路径、方向、连线标签与分组归属，输出影响面清单；带深度上限、分页与稳定的排序。
- **验收**：一跳结果与 `get_context` 一致；多跳结果可用源 JSON 核对；深度上限与分页有测试；对 5000 条量级的包在百毫秒级返回。

### P1-4 URL 反向索引 · M

- **现状**：实例聚合只在单个源内（`sections` / `source_instances`）；清单层已有 `u-<hash>` 的 URL 身份，但只在研究任务里使用。
- **改动**：加一层 URL → 实例的查询：给定 URL 返回全部 `source_id / section_id / item_id`、所在栏目、路径与首次出现时间，可按源过滤；不改变现有 `unique_urls` 的计数语义。
- **验收**：跨源查询可复现且有序；计数与单源查询一致；新增测试覆盖同一 URL 多实例、多源、副本卡三种情形。

### P1-5 轮询开销预筛 · M

- **现状**：每次检查都重读全部候选文件的字节并做 sha256。当前包 37 文件、约 2 MB，实测 0.014 s，每秒轮询约合单核 1.4%；包再大就线性上涨。
- **改动**：先用 mtime 与 size 预筛，只有二者变化才读字节算哈希；命中预筛即视为未变。保持“字节哈希为准”的最终判据不变，并保留一条可强制全量校验的开关。
- **验收**：无改动轮询的耗时随包体量近似持平；人为改内容但保持 size 的用例必须仍被识别（预筛失效有测试）；强制全量校验结果与预筛路径一致。

## P2 搜索层：补齐宪章缺口

这一层动网络、预算与供应商抽象，风险最高，放在索引层稳定之后。

### P2-1 浏览器渲染抓取 provider · L

- **现状**：没有无头浏览器，也没有爬虫：代码只识别 `challenge_blocked` 与 `js_shell_suspected`，不会去解；抓取只走 HTTP 供应商瀑布流。宪章里的“Cloudflare 并发或爬虫类”目前为空。
- **改动**：新增一个可选的渲染 provider（Playwright 或 CDP 驱动本机浏览器），实现现有 provider 契约与 schema 校验，产物走同一条存档路径与内容状态分类；默认关闭，需显式配置才启用；预算与 fair-share 记账复用现有机制。
- **验收**：对 `js_shell_suspected` 的 URL，开启后能取到正文并落档；未配置时行为与现在逐条一致；超时、崩溃、并发上限都有测试；不引入新的必需依赖到默认安装路径。

### P2-2 宿主搜索回流契约 · M

- **现状**：`routing.py` 只探测宿主有哪些搜索工具并转成建议，插件进程无法调用它们；宿主搜到的结果也没有统一入口送回插件归档与去重。
- **改动**：定义一份宿主结果批次格式（与 `search_web` 的归一化结果、`merge-results` 对齐），宿主可把结果按格式交给插件，由插件统一按 URL 与 sha256 去重、落档、打分。
- **验收**：宿主结果与插件结果合并后无重复；来源标注保留；有一条端到端示例与测试；插件仍不反向调用宿主。

### P2-3 agentic 搜索的循环与改写 · M

- **现状**：`agentic_search` 是单次调用：一个答案加一组引用，引用不参与 URL 排序；没有“模型自己管理搜索过程”的迭代，也没有把问题改写成多路查询的步骤。
- **改动**：加一个受预算约束的迭代模式：改写查询 → 检索/读取 → 依据缺口再问，轮数与预算上限显式，每轮独立留回执；关闭时行为不变。宿主模型继续作为可选的改写器，由宿主侧发起。
- **验收**：开启后每轮有独立回执与预算记账，超限即停；关闭时与现在逐条一致；有一份“问题 → 多轮查询 → 证据”的可复现示例。

### P2-4 deep research 通道的就绪与配置 · S

- **现状**：`professional_research.enabled=false`、provider 为 null，凭据文件不存在、环境变量也没有相关 key，所以这条通道目前不可用，而且缺少一眼能看懂的缺项提示。
- **改动**：在就绪诊断里对“开关关闭 / 缺 key / provider 未选”分别给出一句可执行的提示；settings 文档补 OpenAI 与 Parallel 的最小配置样例。
- **验收**：一次诊断调用即可指出缺什么、去哪配；配置齐全后 `research_service_prepare → start` 能跑通最小用例。

### P2-5 缓存默认值与成本说明 · S

- **现状**：`search.cache_seconds` 与 `fetch.reuse_seconds` 默认都是 0，跨调用没有复用；重复提问会重复计费。
- **改动**：给出按场景的推荐值（研究与问答分开），并在设置说明里写清“复用会带来多久的陈旧窗口”。默认值保持保守，只改文档与向导建议。
- **验收**：文档里每个值都能对应到一条真实计费或时延影响；向导设置后行为可在一次重复查询里验证。

## P3 Wiki：提热度、补关联、去重

结构已经够严谨，问题在使用率与关联粒度：5 个页面配 165 个存档正文页，书签级的引用还断在快捷写入路径上。

### P3-1 研究结束后默认入库 · S

- **现状**：`wiki.after_research` 是 `suggest`，所以每次研究都停在“候选”而没落成页面，最后写入停在 2026-10-19。
- **改动**：默认改为 `auto`，仍保留逐次授权语义与 `expected_revision` 冲突即中止的约束；无合格 claim 时明确跳过而不是静默。
- **验收**：一次研究后，存在合格 claim 即产出页面并回报 page_id 与 revision；冲突场景中止且不覆盖；跳过场景给出原因。

### P3-2 存档按 URL 归并 · M

- **现状**：同一次检索里，同一个 URL 的 4 次抓取各占一条结果，因为合并键是正文哈希而不是 URL。
- **改动**：结果默认按 URL 归并，标出最新与最旧捕获，并提供展开参数看全部版本；正文级去重与 sha256 校验保持不变。
- **验收**：同一 URL 多捕获默认占一条且能看到版本数与时间跨度；展开后逐条可读；历史版本仍可单独取用。

### P3-3 补上书签级引用 · M

- **现状**：走 `sources` 快捷写入的页面没有任何 `bookmark_refs`（实测某页 7 条引用全为空），所以无法从页面反查到具体书签；只有走研究任务的路径才带 `{source_id, section_id, item_id}`。
- **改动**：允许 `sources` 项携带书签引用或清单引用，写入前校验存在性与归属，落到 citation 上；缺失时保留为未知而不是伪造。
- **验收**：新页在 `wiki_get` 里能列出具体书签；引用不存在的条目会被拒绝；旧页不受影响且仍可读。

### P3-4 页面检索加权与别名可配置 · M

- **现状**：排序是 `Σ(min(词频,20) + 标题命中 5)`，没有 idf、没有字段权重、没有时效项；别名表是硬编码的 3 组。
- **改动**：加标题与 heading 权重、按命中页面数做类似 idf 的归一（与 `plan_scope` 同一套思路）、别名表可从设置扩展。
- **验收**：用既有的检索校验脚本做回归，召回不降；人工问题上排序更合理；别名扩展后不产生跨组串扰。

### P3-5 重复概念提示 · S

- **现状**：两个页面可以覆盖同一 URL 且没有任何提示，实测已经出现一例；也没有合并机制。
- **改动**：写入时比对既有页面的 URL 依赖与近似标题，给出重叠警告与候选合并对象，只提示不自动合并。
- **验收**：制造一次重叠写入能被提示；无重叠时无噪声；提示可被显式忽略。

## P4 测试与发布

把这次实测用的东西固化成仓库资产，并补上索引审计发现的测试空洞。

### P4-1 补测试空洞 · M

- **现状**：未被覆盖的场景：同 `section_id` 改 label 或 title、同一 live 源的并发写、发布阶段被中断、超大增量、同目录多源。
- **改动**：逐项补用例，沿用现有夹具风格与事务回滚断言。
- **验收**：五个场景各至少一条测试；全量单测通过。

### P4-2 同步基准脚本入库 · S

- **现状**：这次的三档耗时是临时脚本测出来的，没有留在仓库里，下次只能重写。
- **改动**：把等价脚本放进 `scripts/`，输出全量 / 无改动 / 单文件改动三档耗时与 diff 计数，接受包路径参数。
- **验收**：在任意包上一行命令可跑并输出稳定格式；无改动重扫超过阈值时给出提示。

### P4-3 验收用例扩展 · S

- **现状**：现有手动验收文档覆盖定点读取与分页，没有覆盖增量同步与多源去重。
- **改动**：增加两个场景与通过标准：加一条书签后不显式 sync 也能查到；同路径重复源被合并后计数与路径唯一。
- **验收**：按文档逐步执行可复现，不需要额外解释。

## 风险与红线

- **打分改动会碰到宿主提示的契约。** 字面命中是插件与画布指南之间的约定，所以分值只做提示、只加不减，且默认关闭，靠开关回退。
- **浏览器渲染会带进依赖与新的失败模式。** 默认不启用、不进入默认安装路径，超时与并发上限先于功能落地。
- **live 监控是常驻线程。** 轮询开销必须在包体量增长时保持近似持平，否则宁可退回“查询前检查”。
- **索引始终是投影。** 任何新增能力都不得写画布包，写操作仍归宿主；派生库、快照与计数一律落在包外。
- **别把本轮变成大重构。** 不改 TUI、不改安装流程、不动既有的回滚与预算机制。

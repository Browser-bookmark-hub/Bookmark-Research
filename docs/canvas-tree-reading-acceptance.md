# Bookmark Canvas 树状定位手动验收

本文用于在两个 GitHub 仓库的改动推送后，安装本地 Bookmark Research npm 包并重启 Codex 后验收。验收范围是新 AGENTS 模板对 Agent 的约束，以及 Bookmark Research 插件的局部树查询约束。它不验证浏览器导出代码是否已清理历史占位字段，也不授权修改书签包。

## 测试前准备

测试数据目录：`<画布包目录>`（例如 `~/Bookmark-Canvas/bookmark/书签画布`）。换环境时替换为实际画布包目录。

1. 确认两个仓库的模板与插件改动已推送。
2. 使用 Bookmark Research 仓库生成的本地 `.tgz` 安装/升级 Codex 插件，不从 npm 拉取线上版本。
3. 完全退出并重启 Codex，重新打开测试数据目录对应的会话。
4. 测试前记录包内文件列表及目标 JSON 的字节大小。不要把全包或大 JSON 全文贴进对话。
5. 选择一个含多个层级的临时栏目 JSON。记录文件路径、栏目 ID、目标 folder/bookmark ID，以及目标附近的父子关系，作为本地核对依据。

小型 JSON 可直接读入上下文；大型 JSON 必须由本地解析工具或插件索引读取必要节点。测试过程只读，不写回源文件。

## 场景 A：仅模板，无 Bookmark Research 插件

在 Codex 中关闭或暂时不可用 Bookmark Research MCP/Skill，只保留画布包提供的 AGENTS 模板及本地文件/终端工具。提交以下提示：

> 请按当前画布包的 AGENTS 模板，只读检查临时栏目中的目标书签。先确认目标文件大小；小文件可直接阅读，大文件请用本地解析工具按目标 ID 或标题定位，不要把整份 JSON 输出到对话。按显式 `type` 区分 folder 和 bookmark，不要因 folder 有 `url: ""` 或 bookmark 有 `children: []` 而误判。请返回源文件路径、栏目/section ID、目标 item ID、准确的父级路径、同级顺序、目标的必要字段，以及为回答读取了哪些父子节点、还有哪些范围未读取。不要改文件；没有 `.canvas` 证据时不要描述卡片坐标或空间关系。

分别选择一个目标书签和一个目标文件夹运行。文件夹测试需说明其直接子项与更深后代的区别；同名候选存在时必须列出候选并用 ID/路径消歧，不能按标题猜唯一结果。

**通过标准**

- 使用本地解析/读取工具，且大型文件没有全文进入对话上下文。
- 目标类型以显式 `type` 判定，空占位字段没有改变判型。
- 返回的文件路径、ID、父路径和同级顺序能与源 JSON 核对一致。
- 明确区分已读取与未读取范围；不把局部样本称作全量检查。
- 源文件在测试前后保持不变；不臆造 `.canvas` 坐标、分组或连线。

## 场景 B：模板与 Bookmark Research 插件共同工作

启用本地安装的 Bookmark Research 插件并重启 Codex。先让 Agent 报告本会话中实际可调用的 Skill/MCP 工具；不能仅凭安装成功推断工具已经加载。随后提交：

> 请依照当前画布包的 AGENTS 模板，只读定位临时栏目中这个目标：`<填入目标书签标题或 item ID>`。优先使用当前会话实际可调用的 Bookmark Research 查询工具；先从指定包/source 找到唯一栏目和 section ID，再按 item ID 读取目标及祖先路径。如果目标是文件夹，请用 `folder_id` 查询其子树并按页读取，只取回答所需节点。明确报告查询的 source/section/item ID、父路径、同级位置、已读条数、总数与 `next_offset`/未读范围。请核对临时项按 `type` 判型，忽略空 `url`/`children` 对类型的干扰。插件结果是索引投影，不要将其当作完整源对象；不要修改文件。若工具不可调用，请说明并退回场景 A 的本地解析流程。

至少执行三次查询：一条已知书签 ID；一个有多层后代的文件夹 ID；一个同名或重复 URL 候选（若数据中存在）。文件夹查询使用有限页大小，至少一次停在非空 `next_offset`，然后继续翻页确认分页边界。

**通过标准**

- 工具来自当前重启后的 Codex 会话，且检索的 source 与实际包一致；没有可用工具时清楚回退。
- 定点结果的祖先链与 `folder_id` 子树结果能用源 JSON 核验；分页的 `total`、每页条数和下一页偏移一致。
- 搜索结果保持书签实例、URL 和不同栏目/路径的区别；重复标题或 URL 不被错误合并为一个位置。
- 条目投影不把空 folder URL 当作链接，也不把 bookmark 的空 children 当作文件夹；原始文件中的这些字段仍然保留。
- 测试前后源包无变化；没有把精简索引结果写回 JSON，也没有声称未读取部分已检查。

## 场景 C：增量同步（新增书签秒级可见）

在已配置为 live 模式的画布包某栏目 JSON 中，手动追加一条带有唯一标题和 URL 的测试书签（记录其 item ID、title、url 及所属父节点）。
在 Codex 中不显式执行 `sync_package`，也不重启插件，直接提交提示词：

> 请定位刚在临时栏目中新增的书签：`<填入新增书签标题或 item ID>`。使用 Bookmark Research 查询工具读取其完整层级路径、父节点与同级位置。明确报告该书签当前的 revision、所在 section ID 及父路径。

**通过标准**

- 监控与查询层自动触发增量刷新，新增书签在秒级内可被检索工具定位。
- 检索返回的新增书签路径、父节点及同级索引与手动编辑的源 JSON 完全一致。
- 仅被修改文件的书签条目其 `revision` 发生递增，画布包内其他未修改文件的条目其 `revision` 与状态保持稳定。
- 画布包内所有源文件保持只读，未被插件回写或篡改。

## 场景 D：多源去重与合并（同路径重复源清理与唯一性）

针对同一画布包路径下重复注册了多个旧源（例如 `index_status` 报告同路径存在多个 source_id，或旧源带着包内已不存在的文件而导致 `retained_missing_files` 非空）的场景：

1. 先使用 CLI 进行干跑比对：
   ```sh
   python3 src/cli.py source merge <重复源ID> <保留源ID>
   ```
2. 确认计数与版本一致后执行正式合并（若内容哈希冲突则改用确认移除）：
   ```sh
   python3 src/cli.py source merge <重复源ID> <保留源ID> --confirm
   # 或
   python3 src/cli.py source remove <重复源ID> --confirm
   ```
3. 在 Codex 中提交提示：
   ```
   请检查当前的索引状态及源列表，确认画布包对应的源是否已唯一，且 retained_missing_files 是否已归零。
   ```

**通过标准**

- 目标路径仅保留一个唯一的有效 source_id，重复源被完全移除或合并。
- 运行 `index_status` 后，所有源的 `retained_missing_files` 计数均为 0。
- 合并/清理后，条目检索与上下文定位均指向唯一保留源，不存在跨源冗余命中或已废弃文件的陈旧投影。
- 整个清理过程未对画布包物理文件产生任何写操作。

# 0.5.0-beta.9 性能与成熟度实测

> 本文保留修复前的测量与建议。各项当前落实情况见 [2026-10-11 升级核对](upgrade-status-2026-10-11.md)，包括已补的轻量来源状态读取和仍未完成的优化。

2026-10-10。结论：**日常小画布查询已经很快，现有正确性检查也通过；下一轮最有价值的工作是解除 MCP 请求阻塞、补齐大画布读取边界、减少查询里的重复 SQL 和全库统计。** 跨提供商搜索、Jina 批量读取、提供商目录缓存和紧凑搜索输出都已有效，不需要重新实现这些能力。

测试实际安装的 `0.5.0-beta.9`，仓库提交为 `b5cba1eed87a1aa30ee7903237c0caf90eb4ebae`。安装目录与仓库的 29 个 Python 源文件逐字一致。优化原型只在隔离进程的内存中执行；本报告不代表已经发布性能修复。

## 测量方式与正确性

- 环境：macOS 15.7.2 / arm64，Python 3.9.6，SQLite 3.43.2，10 个逻辑 CPU。
- 真实包：7 个文件、326,282 字节；638 个书签实例、557 个唯一 URL、5 个栏目、7 个画布节点、3 条边。122 个文件夹行包含 1 个合成根，用户文件夹为 121 个。
- 独立读取原始 JSON，与查询全部 7 页得到的 URL 多重集合一致；实例身份未合并。A 和副本 B 各自查询都返回 601 条，但全包仍为 638 条。
- 紧凑查询的顶层页面与各关键词独立页面分别核对，包括 `limit=1` 的目标独有结果；计数、顺序和身份一致。
- 现有测试：595 项，592 通过、3 跳过、0 失败，耗时 123.774 秒。原包全部 7 个文件的文件集和 SHA-256 前后相同。
- 本地常规测量预热 2 次、采样 20 次；放大样本采样 10 次。小样本 p95 采用 nearest rank，仅作描述。首次导入为单次观测；系统文件缓存没有清空。
- 本地性能通过已安装插件的真实 stdio MCP 进程测量，包含协议序列化和进程间传输；不包含模型思考和宿主界面展示。另单独测当前会话中的真实联网工具调用。
- 索引、快照、放大数据均在独立目录。联网只使用公开的 SQLite/Python 文档，抓取设置为 `archive:false`。

首次新建索引并导入约 **102 ms**；相同包再次同步中位数 **11.02 ms**，没有产生新内容版本。新进程启动至 MCP 初始化完成中位数 **50.32 ms**；每次重开 CLI 做同一 Exa/MCP 查询为 **67.83 ms**。批量任务复用常驻 MCP 有明确价值。

紧凑 Exa/MCP 正文减少 **54.0%**，代价是本地处理多约 **0.43 ms**。这是合理的传输取舍，但不能据此宣称模型回答加速 54%。计数页没有书签行可去重，额外加 `compact:true` 反而多 261 字节，因此计数直接用 `count_only:true` 即可。

2025-11-25 协议同时返回文本与 `structuredContent`：上述紧凑查询的实际线路消息为 14,514 字节，完整查询为 31,448 字节。两份表示用于客户端兼容；是否都进入模型上下文取决于宿主，不能直接按线路字节换算 token。若进一步精简，应先测宿主实际收到的内容。

这些受控回放使用真实调度实现，替换的是网络传输或慢搜索结果，**不是外部服务速度测试**。

真实联网另执行 4 次公开查询、3 次双 URL 抓取：

- 首轮同时提交 search/fetch，搜索在 5.180 秒完成，抓取在 6.185 秒完成。后者包含同连接排队，不能当成抓取自身耗时。
- 后续独立提交的热搜索为 1.733、1.767、1.694 秒；两次热抓取为 1.000、0.993 秒，每次取得两个文档各 3,000 字符。这是部分正文读取。
- 冷搜索产生 8 个 HTTP 请求，包含两组初始化和目录发现；热搜索只需 2 个 HTTP 请求，`cache_hits=2`。缓存复用正常。
- 四次搜索成功提供商数为 2、2、1、2；全部仍有可用结果，未触发备用提供商。第三次的初始采样只保存成功数，未保留分批错误详情，因此无法归因；追加诊断中两个提供商均恢复成功。这也是应完整保留每个提供商状态和错误分类的理由。

此联网样本用于验证通路、缓存和排队现象，次数不足以估计服务 SLA 或稳定的网络 p95。

## 放大后暴露的开销

构造 638 / 6,380 / 63,800 个实例的扁平栏目：重复真实书签的标题、URL、备注和标签，分配独立实例 ID；唯一 URL 始终为 557。它保留部分查询选择性，用于检查索引增长，**不等同于三个真实规模的完整画布**，不包含原有文件夹和空间关系。

以下为查询引擎本身的中位数，尚未加 MCP 的来源状态封装。

| 操作 | 638 实例 | 6,380 实例 | 63,800 实例 |
| --- | ---: | ---: | ---: |
| 全包计数 | 0.42 ms | 5.54 ms | 162.38 ms |
| 两字中文「模型」 | 2.89 ms | 21.13 ms | 405.30 ms |
| 长关键词「GitHub」 | 1.37 ms | 6.32 ms | 69.48 ms |
| 6 个混合关键词 | 7.57 ms | 60.91 ms | 990.24 ms |
| 栏目上下文 | 1.22 ms | 12.84 ms | 176.14 ms |

63,800 实例首次导入约 **7.81 秒**，无内容变化的同步仍为 **1.31 秒**。相同数据在完整 MCP 业务分发中，六关键词查询为 **1.100 秒**，计数为 **274.94 ms**，上下文为 **286.34 ms**。

性能剖析给出了三个具体原因：

1. 六关键词调用约 1.103 秒，其中 SQLite `execute` 累计 1.093 秒。紧凑投影约 3 ms，继续抠投影字符串的收益很小。
2. 查询结束都会额外调用完整来源 `status`，单次约 **115 ms**；它重新统计全库，并通过 `SELECT *` 读取栏目记录。即使搜索只命中少数行，也承担这笔成本。
3. 上下文只返回栏目头部，但先读取并解析整份栏目 `raw_json`，再剔除 `tree/items/identityMap`。单个大栏目下可见这部分开销，且还有全范围 URL 统计。

相比之下，该放大数据的无变化 live 检查只增加约 14 ms：`refresh:false` 计数 275.31 ms，`refresh:true` 288.92 ms。因此本例应先处理 SQL 和状态统计。

### 已验证的局部优化原型

单关键词请求的总页面与唯一 target 页面查询相同，当前会分别执行；计数模式记录到两条完全重复的 SELECT。

隔离原型只复用这份单关键词查询结果：

| 63,800 实例上的操作 | 原实现 | 原型 |
| --- | ---: | ---: |
| 单关键词计数 | 62.10 ms | 31.07 ms |
| 单关键词紧凑页面 | 67.30 ms | 33.87 ms |

完整响应逐字段一致。另用真实小包对照 64 组参数组合，覆盖空/单/多关键词、无命中、计数、紧凑/完整格式、零 limit、偏移和越界页。这里约减半的是查询引擎的这段工作；来源状态开销仍在，不能把收益外推为整次 MCP 调用减半。

### 大画布读取的功能边界

另构造 **5,000 个独立文本节点**，每个节点约 200 个 ASCII 文本字符。内部 context 可返回全部节点，但正文为 **3,747,426 字符**，超过 MCP 的 **2,097,152 字符**上限，工具最终只返回错误。

错误建议 `paginate with a lower result limit`，而 `get_context` 实际参数仅有 `source_id / section / group_id / item_id / refresh`，没有 limit、cursor 或按画布节点 ID 读取的参数。该样本没有可据以分割的栏目和组，提示不能完成恢复。CLI 可以绕开 MCP 大小检查，但需要的 MCP 分页能力确实缺失。

## 建议的实施顺序

| 优先级 | 改进 | 实施与验收重点 |
| --- | --- | --- |
| P1 | MCP 外层异步调度，避免慢网络挡住本地读取 | 保留有界并发、请求 ID、取消与总时限。每个工作线程使用自己的 SQLite 连接；维护同来源/研究任务的写入顺序和锁。验收：挂着慢请求时，本地快查仍接近独立调用时延。 |
| P1 | context 支持可完整遍历的大结果 | 增加摘要/分页或按节点读取，带来源版本与稳定游标，保留边端点和组关系。验收：5,000 节点全部可取回、无遗漏，错误给出真实可用的恢复参数。 |
| P1 | 消除重复 SQL 与每次查询的全库统计 | 先落地已验证的单关键词复用；再将不随查询变化的来源计数按输入版本保存，提供轻量状态读取。状态新鲜度和副本计数语义继续保留。 |
| P2 | 输入未变时减少同步的临时写入与重复读取 | 在哈希、模式、完整性策略、绑定关系均未变化时复用同一版本；保留快照校验与原子提交。避免把模式切换或 partial/complete 切换误判为无操作。 |
| P2 | 把栏目头部与完整原始树的读取分开 | 常规上下文读取头部；完整原始字段保留为可展开证据，减少无用的整树解析。 |
| P2 | 增加性能与交互回归指标 | 固定小包、大索引、大画布、慢/失败提供商四类场景；分别记录排队、执行、序列化、输出字节、首批可用证据时间、提供商错误和覆盖率。用稳定环境的相对回归阈值，避免拿本机绝对时延直接做跨平台 CI 门槛。 |

并行应集中在彼此独立的网络读取和只读任务。当前同提供商的会话、用量计数和限流状态共享，扩大其并发需先设计连接池与配额归属；两字中文检索也必须继续保持字面子串语义。

当前会话已有 6 个基础入口。用相同 JSON 编码计算，这 6 个入口目录约 5,041 字节，全部 40 个契约约 38,019 字节。下一轮不需要为了工具名字更少而合并职责；优先使用批量 targets、按需 context、计数页和已有结果复用。若要评估用户最终感受到的响应，还应做固定提示词与相同模型的首答时间和答案完整性对照，本轮没有把 Python 耗时当成这些指标。

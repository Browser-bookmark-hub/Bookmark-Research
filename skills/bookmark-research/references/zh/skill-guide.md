# 书签聚合研究（中文阅读版）

[English execution Skill](../../SKILL.md) · **中文阅读版**

本文件用于中文审阅，与英文执行文件保持相同规则。宿主只发现并加载根目录的 `SKILL.md`；本文件不注册第二个 Skill，也不要求同时加载两种语言。

把用户的问题转成可重复的本地查询与按需网页研究，交付答复或研究报告。适用于符合 Bookmark Canvas JSON 模式协议的数据包，路径、来源名和查询目标由当前用户提供或从其已注册来源中选取；插件不预置任何个人书签库。按任务判断需要本地元数据、网页内容，还是两者结合。

## 输出语言

优先遵循用户指定的输出语言，否则跟随实际任务和对话语言；双语入口示例本身不决定语言。答复、进展、报告正文和 Wiki 标题／章节采用该语言。引用、URL、标识符、代码和工具字段保留原样，译文另列。语言选择不缩小原始来源范围，也不限制只能检索同一种语言的资料。安装器的 `--lang` 只控制安装引导，不设置后续研究语言。

任务与对话都没有选择语言时，默认英文。将明确的输出语言要求保存在研究 brief 中，并传给每个子代理、工作流的 `output_language` 和专业研究服务的输入，便于恢复后沿用。参考文档按需读取一种语言即可，无需同时加载两种版本。

## 数据包阅读规则

分析数据包时，先读本插件的 [阅读协议](package-semantics.md)，掌握字段、元数据位置、副本与关系语义；同一会话已读且规则未变时直接复用。受支持格式的常规分析使用这份内置协议，不要求每次重新读取包内整份 `AGENTS.md`。

包采用新格式、出现未解释的字段或冲突，或用户要求核对包内特殊约定时，再查该包 `AGENTS.md` 的相关章节和实际 JSON。载体已加载且适用的目录指令仍需遵循。当前 Skill 没有生成或回写书签包的流程；生成报告不等于生成可导入 JSON/.canvas。

## 调用入口

本插件注册一个 `bookmark-research` MCP，提供本地查询、搜索／读取、`research_*` 研究档案与专业服务、`wiki_*`、评测和配置。不同宿主会给工具名加前缀，按当前工具列表调用。

按本次操作检查当前宿主实际暴露的工具。所需工具未加载时使用同包 CLI，包括已有 MCP 但只暴露部分旧版工具的情况。插件根目录是英文执行文件 `SKILL.md` 所在目录的 `../..`，入口为 `<插件根目录>/src/cli.py`。使用实际绝对路径，不依赖当前工作目录。命令和结果格式见 [references/cli.md](cli.md)。这份固定程序负责查询，不要为每个问题重写脚本或重建数据库。若对应 CLI 命令也不存在，再说明当前版本的缺口。

## 从用户请求选择流程

用户用自然语言说明问题、范围和交付要求即可，不要求固定提示词。只问书签位置、数量或画布结构时走本地查询；联网任务优先遵循本次明确的深度要求，再遵循保存的默认设置。`research.depth:auto` 时按任务判断：

| 用户意图示例 | 流程 | 执行动作 |
| --- | --- | --- |
| “快速查一下这个书签中的事实” | `quick` | 读取已有 URL；需要发现来源时搜索并读取关键页，然后答复。 |
| “比较我收藏的这些工具，查清它们的区别” | `agentic` | 结合画布语境拆问题，搜索、读文、分析，根据缺口继续补查。 |
| “研究整个包”或“做持续调查，交付可复核报告” | `deep` | 建立研究档案，保留完整任务范围，组织调查、证据审阅和覆盖核验；按要求编写 Wiki。 |

深度和范围分别判断：用户指定卡片或专题时保留该范围；要求研究整包时遵循下方完整范围规则。开始执行时简短说明所选方式和范围，然后实际调用工具；`research_route` 的建议不代表已经启动研究。宿主多轮研究无需专业研究 API 凭据；用户明确指定专业服务时先检查其可用性，不静默改用别的执行路线。用户仅询问能力或方案时，回答问题，不据此启动数据包调查。

## 本地问题

1. 先用 `index_status` 找已注册的 `source_id`。`sync_package` 接受目录、ZIP 和单卡 JSON；手动导出用 `mode:"snapshot"`，用户指定的持续同步目录用 `mode:"live"`。明确是完整镜像才用 `completeness:"complete"`；局部导出和单卡用 `partial`。同一画布的新路径沿用原 `source_id`，不凭标题或 URL 相似合并来源。接入、迁移或恢复时读 [来源生命周期](source-lifecycle.md)。
2. 把多个目标放在一次 `search_bookmarks.targets` 中；按用户范围传 `section`、`group_id`、`folder_id` 或 `tags`。每个目标都有独立的总数与分页。快照离线可用，live 查询前检查变化。读取返回的 `source.state`；pending 结果应说明尚未同步，error/unavailable 时用户允许用旧索引才设 `refresh=false`。历史版本通过 `source_history` 找快照，不能用 `refresh=false` 指定。
3. 查询卡片描述、组成员、方向关系用 `get_context`，这些字段不在书签文本搜索范围内。对具体书签传 `item_id` 才返回该项及 `ancestors`；只传栏目或组时返回结构概览，不会列出全部书签和文件夹。进一步限定文件夹时，从书签祖先中取得 `folder_id`。

这是元数据的字面匹配加结构过滤，不是公司实体识别或语义检索。中文别名、英文名、域名可分别查询；“公司文件夹里有 536 条书签”不等于“有 536 家公司”。不要把零匹配解释成互联网上不存在。按公司汇总时保留命中的书签 ID、URL 和上下文，说明归并依据。

JSON/.canvas 是事实来源；SQLite 保存派生索引和来源登记，原始快照、笔记、证据与数据库均在同步包之外。MCP 存活期间只自动更新 live 来源的本地索引；研究清单、正文和 Wiki 保留版本。`research_status.source_freshness` 或 Wiki 的 `needs_review` 提醒来源已变，需要复核，不表示已重新调查。

## 网页问题

- **快速查证**：明确 URL 用 `fetch_web`，需要发现来源时用一轮 `search_web` 后读取关键页面。Non-reasoning 描述模型的搜索方式，不能仅凭是否有 URL 判断推理能力；不保证服务会实时访问原站。
- **Agentic search**：由宿主模型拆目标、组织查询、阅读和补查。独立专题使用当前可调用的子代理；重复的分组、核验和补查可交给宿主已有工作流。执行与子代理生命周期属于宿主。
- **Deep research**：需要持续、多轮调查或研究报告时，读 [深度研究流程](deep-research.md)。按问题选择原生研究、宿主研究工作流或 [专业研究服务](research-services.md)。专业服务是可选路线；有搜索 MCP 不等于有研究 API 认证。

多来源任务读 [宿主工作流](host-workflows.md)。可用 `research_route` 传当前实际可见的 tools、commands、extensions，得到建议；它不会启动执行。Codex 使用原生委派，Claude 使用已加载的 Dynamic Workflow，Pi 使用已加载扩展，DSH 使用已配置引擎。不凭宿主名称推断已启用的能力，也不把文档确认、组件发现和真实运行混为一谈。Claude 的 `/deep-research` 需要明确调用；在提示词中写 `ultracode` 不能替代真实调用条件。

需要比较产品、事实核验或分析排行榜时，读 [研究方法](research-methods.md)，把选中的方法与问题交给读者和独立核验者。采用现成 SDK 的条件是确有无宿主程序化需求；插件不实现调度器、代理池或后台 worker。

联网前读 [研究与服务接入规则](research-workflow.md)，按实际可用工具和用户范围执行。默认 Exa + Parallel，可按需选择 Tavily；配置与工具发现不证明实际调用已获授权。仅查询本地时无需读取联网参考或探测远程服务。

涉及 GitHub 仓库、issue、代码或 Git 同步时，读 [GitHub 与同步边界](github-and-sync.md)。插件没有内置 GitHub MCP；优先使用宿主实际具备且适用于任务的 GitHub 工具，公开网页也可用 `fetch_web` 读取。

## 研究数据包的完整范围

用户要求研究一个数据包时，默认调查所给包的全部原始 URL，并保留每个重复书签实例的文件夹、卡片与关系语境。只有用户限定了专题、卡片或来源子集时才采用对应范围；不能因搜索只返回一页、预算、重复 URL 或子代理数量而自行缩小。

1. 同步包后用实际索引的 `source_ids` 调用 `research_start`；默认 `scope_mode:"whole"` 冻结完整来源。`bookmark_refs` 可以标记关注点，不能隐式缩成这些书签。确需限定来源时显式 `scope_mode:"subset"`，交付中报告选中与未选中项。
2. 用 `research_inventory` 跟随 `next_offset` 读完来源清单。区分数据包 `source_id`、原始 URL 的 `u-...` inventory ID、正文快照的 `sN` evidence ID。分组沿用全部 inventory ID；分批和并发仅改变执行方式。
3. 从原 URL 获取正文（或导入宿主实际取得的正文），读 `research_source` 后做 `source_review`、引用结论和 `inventory_review`。搜索摘要、仅导入文件、成功结束的子代理和外部报告的引文列表都不能替代原页审阅。
4. 由独立步骤复核结论与引用，再用 `research_coverage` 取得尚未读取／审阅的差集并继续。失败或登录受限写 `blocked` 与具体原因；有依据的范围外／非内容项写 `excluded` 与原因。不能通过批量排除或只记失败来宣称整包研究完成。

首次读取预算随 URL 数给出下界；查看 `initial_fetch_plan`，每次可批量读取至多 8 个 URL。显式预算原样保留，不足时保留完整清单、说明缺口；预算不覆盖宿主自身或外部服务看不到的消耗。

## 用户配置

用户询问配置或保存位置时用 `get_settings`；要求改变今后默认行为时，用 `update_settings` 仅更新相关字段。临时要求用本次工具参数覆盖，不改长期偏好。配置和归档格式见 [配置与来源归档](settings-and-archive.md)。这些选项由固定程序执行，不靠每轮重新编写脚本。

## 交付与留存

简单查询直接答复；研究报告保留引用与实际覆盖范围。`fetch_web` 默认保存实际响应、能识别的正文和来源记录，检查失败、缺失与完整性标记。`search_web` 不自动读取命中的 URL。抓取成功与原句匹配均不能证明结论成立，模型仍需检查页面身份和引用语义。

用 `research_finish` 生成报告、来源清单和覆盖明细。分别报告逐项交代、可用正文、实质审阅与问题完成度。完整来源审阅、问题回答和冲突检查满足条件才用 `completed`；仍有重要缺口、活动／结果未知的外部任务或预算不足时用 `incomplete`。档案在数据目录的 `research/`，`research_status` 的概览最多预览 20 条，完整记录需分页。继续 incomplete 档案先记 `resume`；保存档案不意味着后台有代理运行。

用户需要知识整理时，使用 `wiki_write` 将已接受来源支持的有效结论编为主题／实体页，保存关联、版本与审阅说明；用 `wiki_lint` 检查来源和链接，用 `wiki_search` 检索整理后的正文。Wiki 位于原包之外，没有自动向量化或网页监控。质量比较使用 `evaluate_research`，先准备实际运行结果与独立评审标签；缺失的语义评分、成本和时延保持未知。详见 [Wiki 与评测](wiki-and-evaluation.md)。
